# Hand-written SQL on the marts (Postgres 18)

Evidence for FL-M1 "Done when" D4: 8 queries over `marts.fct_financials` (1,410,590 rows) and the dimensions, each measured before and after one index change.

- **Current results:** [`RESULTS.md`](RESULTS.md) (generated by the runner; times, rows, first scan node of each plan).
- **Full plans** with buffer counts: `explain/NN_name.before.txt` and `explain/NN_name.after.txt`.
- **CSV:** `../bench/sql_explain.csv`.

## Setup

- `compose.yaml`: `postgres:18` (measured: PostgreSQL 18.7), localhost only on port 55432. Fixed settings: `shared_buffers=1GB`, `effective_cache_size=4GB`, `work_mem=64MB`, `jit=off`, `track_io_timing=on`.
- The marts are copied from the dbt DuckDB file with **no keys or indexes**: `python -m filinglens.sql.load_postgres` → `../bench/postgres_load.json`.
- Machine: laptop (Ryzen 9 8940HX), Postgres in Docker Desktop on WSL2. Warm cache: the marts fit in `shared_buffers`.

## Method (`python -m filinglens.sql.explain_bench`)

For each `NN_name.sql`, with its partner file `NN_name.index.sql`:
1. Drop every index in schema `marts`, so the baseline is clean, then `ANALYZE`.
2. Run the query once to warm the cache, save one `EXPLAIN (ANALYZE, BUFFERS)` plan, then time 5 runs of `EXPLAIN (ANALYZE, TIMING OFF)` and keep the median `Execution Time`.
3. Apply the index file, `ANALYZE`, and repeat step 2.
4. Check that the result is identical before and after (sha256 of the sorted rows). The runner stops if it isn't.

`TIMING OFF` is used for the timed runs: per-node timing reads the clock for every row and inflates fast queries. The saved plans keep per-node timing. Times are measured inside the server and exclude sending rows to the client.

## Queries

| # | File | Question | SQL features | Index change | Technique |
|---|---|---|---|---|---|
| 01 | `01_yoy_revenue_one_company` | Apple's year-over-year annual revenue growth | `LAG()` window | `(cik, tag, duration_quarters)` | equality columns; `cik` first, so one-company queries can use the prefix |
| 02 | `02_sector_revenue_rank` | Top 5 by annual revenue in each sector, periods ending in 2024 | `DISTINCT ON`, `RANK() OVER (PARTITION BY …)` | `(tag, duration_quarters, value_date)` | equality columns first, then the range column |
| 03 | `03_rolling_4q_avg_assets` | Rolling four-quarter average of total assets, retail | window frame `ROWS BETWEEN 3 PRECEDING AND CURRENT ROW` | `(tag, duration_quarters, cik, value_date) INCLUDE (unit, value)` | covering index: index-only scan, rows already in window order |
| 04 | `04_first_year_tag_reported` | First period each company reported the operating-lease right-of-use asset (ASC 842) | `min()` per group, then a histogram | `(tag, cik, value_date)` | `min()` per group read from index order |
| 05 | `05_revenue_decline_streaks` | Longest streaks of consecutive yearly revenue declines | gaps and islands (`year - row_number()`) | partial index `... WHERE duration_quarters = 4 AND unit = 'USD'` | indexes only the rows the query can use |
| 06 | `06_gross_margin_cte_pipeline` | Gross margin per company, periods ending in 2024 | CTE pipeline (one CTE used twice, materialized) | expression index on `extract(year from value_date)` | sargability: a plain `value_date` index can't serve `extract(year …) = 2024` |
| 07 | `07_peer_self_join` | The 10 sector peers closest to Apple in annual revenue | self-join of the fact table | `(cik, tag, duration_quarters, value_date) INCLUDE (unit, value)` | serves the inner side of a nested-loop join |
| 08 | `08_net_margin_percentiles` | Net-margin quartiles per sector, periods ending in 2024 | `PERCENTILE_CONT … WITHIN GROUP` | `(tag, duration_quarters, value_date) INCLUDE (cik, unit, value)` | covering version of 02's index (index-only scan) |

## Findings (measured 17 Nov 2026; current numbers in RESULTS.md)

- **Selectivity decides the gain.**
  - 01 reads 9 of 1.41M rows. Before: a parallel sequential scan of 38,914 buffers. After: an index scan of 11 buffers (40.514 → 0.023 ms in that run).
  - 06 still reads 21,251 rows through its expression index, so it gains about ×3.
- **A planner misestimate, fixed by a rewrite, not an index** (first version of 03):
  - Postgres can't estimate a filter on window-function results, so it assumed 1 row for `points = 4 AND span_days BETWEEN …`.
  - It then joined `dim_company` as a nested loop: it scanned all 300 rows once per result row (1,604 times), with 479,596 rows removed by the join filter.
  - With the covering index alone: 46.724 → 23.473 ms (×1.99).
  - Joining `dim_company` once, before the window, brought it to 45.119 → 3.075 ms (×14.67), using a merge join and an index-only scan with 0 heap fetches.
- **Covering vs. plain index:** 08's `INCLUDE` index gives an `Index Only Scan` with `Heap Fetches: 0`. 02's plain index still visits the table for each row.
- **Partial index (05):** Postgres uses it only because the query's `WHERE` implies the index's `WHERE`. Without `unit = 'USD'` in the query, the index would be skipped.
- **07:** the date range is applied as a join filter (571 rows removed in that run), not as part of the index lookup.
- **Tag choice (04):** `OperatingLeaseLiability` is used by only 10 companies, `OperatingLeaseRightOfUseAsset` by 174, so 04 uses the latter. 84 companies first report it in 2018 and 3 in 2017, earlier than most companies' effective date. The cause isn't checked yet (see `docs/LATER.md`).

## Known limits

- **Revenue** is one tag per company and period, taken from a priority list (`Revenues`, `RevenueFromContractWithCustomerExcludingAssessedTax`, `…IncludingAssessedTax`, `SalesRevenueNet`).
  - Banks and insurers often report revenue under other tags, so they're under-covered.
  - A company that switches tags between years can show a false decline in 05.
- **"Periods ending in 2024"** means fiscal periods whose end date falls in calendar 2024: Walmart's fiscal 2024 ends on 2024-01-31.
- **The timings come from one laptop with a warm cache,** as the median of 5 runs. Compare the before/after pairs with each other, not with other machines.

## Reproduce

```bash
set -a; source .env; set +a
docker compose up -d --wait
uv run python -m filinglens.sql.load_postgres        # copy the marts, no indexes
uv run python -m filinglens.sql.explain_bench        # all 8; or a name filter, e.g. "03"
docker compose down -v                               # teardown (deletes the Postgres volume)
```
